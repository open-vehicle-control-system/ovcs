# vision_api

Phoenix endpoint of the vision unit. It serves the [dashboard](../dashboard) build and exposes `VisionCore` to it. [Vision API](../../docs/vision/api.md) and [Vision channels](../../docs/vision/channels.md) show how a program uses it, with examples.

The `/api` routes follow [JSON:API](https://jsonapi.org/): a response is `application/vnd.api+json`, and a refusal's `errors` list holds one error object with `status`, `title` and `detail`. A refusal of the request document points at the member at fault with `source.pointer`, as do the 404s for a calibration or a saved calibration the document names. One of a query parameter names it with `source.parameter`: an `include`, a `sort` or a `filter`. The others (a 404 for the resource in the path, the 503s and a refused reset's 422) have no `source`. An unknown `/api` path answers a 404 whatever the client accepts, and a known one sent another method a 405 whose `allow` header names the methods it takes. A `POST` whose document carries an `id` is a 403: the unit names what it creates. An error raised outside the controllers is an `errors` list too: a 500 with `status` and `title`, a body that is not JSON (400) and an `Accept` header that takes no JSON (406) with a `detail` as well.

Every route answers:

- a 400 for a path whose id is not valid UTF-8 (`VisionApiWeb.JsonApi.check_path/2`);
- a 400 for a `sort`, and for an `include` on any route but `GET /api/stages` and `GET /api/ros2-node` (`VisionApiWeb.JsonApi.check_query/2`);
- a 503 titled `Vision core unavailable` while the vision core does not run, is restarting or does not answer in time (`VisionApiWeb.Core`).

A write reads its document from a JSON body only: sent as a form or in the query string, it is missing, and the answer is a 400.

| Route | Answer |
|---|---|
| `GET /api/stages?include=parameters` | The `stages`, one per `VisionCore.Parameters` group, by position: `name`, `summary`, `explanation` (a paragraph on what the step does, why it matters, what its settings change and what to watch, or `null`), `pipeline` (the pipeline it is a step of, such as `stereo` or `detection`), `position`, `status`, `role` (`source` for a component, `step` for a stage) and, for a pipeline stage, `compute`: where it runs (`runsOn`: `cpu`, `gpu` or `npu`), what it is written in (`implementation`: `nx`, `rust` or `elixir`) and what compiles Nx (`backend`: `vulkan`, `llvm_cpu`, `exla` or `evaluator`), their parameters in `included`, the unsaved count in `meta.unsaved`; 400 for any other include. |
| `GET /api/parameters` | Every parameter, the unsaved count in `meta.unsaved`. A parameter has `name`, `valueType`, `constraint`, `applies`, `description`, `default`, `value`, `saved` and `state`, and relates to its `stage`, the parameter it must stay `greaterThan`, and the automatic mode it is `controlledBy`. |
| `GET /api/parameters/:id` | One parameter; 404 when unknown. |
| `PATCH /api/parameters/:id` | Sets one as an unsaved change: 200 with the parameter, 422 when refused, 404 when unknown, 409 on a `type` or `id` mismatch, 400 without `data.type`, `data.id` or `data.attributes.value`. |
| `POST /api/parameter-saves` | Saves the unsaved changes: 201 with the saved parameter ids; 503 when the store fails, 409 for another `data.type`, 400 without one. |
| `POST /api/parameter-discards` | Discards the unsaved changes: 201 with their ids; 409 for another `data.type`, 400 without one. |
| `POST /api/parameter-resets` | Resets the `target` relationship (a `stages` or `parameters` resource), or everything without one: 201 with the reset ids; 404 for an unknown target, 422 when a parameter's owner refuses, 409 for another `data.type`, 400 without one, or for `relationships` that do not hold a well-formed `target` of those types. |
| `GET /api/exporters` | What takes the unit's outputs out of it: each of its `exporters` (`VisionCore.Exporters.describe/0`), identified by its id (`ros2` for the ROS 2 exporter), then the API itself, `api`. An exporter has `name`, `module`, `actions` (each with a `name`, a `label` and a `description`; none for the API) and `outputs`, those of the unit it reads. Each output has a `name`: `stereo_pair`, `camera_frame:left`, `camera_frame:right`, `camera_frame:<name>` for each camera of its own, or `camera_frame:<name>:<output>` for an output other than its default, `camera_video:<name>:<output>` for a camera's H.264 video, `detections:<name>` for each detection pipeline, `detections:detection` for a detector without a name, and `segmentation:<name>` for each segmentation pipeline. Its `maxHz` is the most values it takes a second, `null` when unbounded; for the API, the rate its channel carries them at. The API's detection and segmentation outputs also have a `source`: `left` for the stereo pair, or the name of the pipeline's camera of its own. |
| `POST /api/exporters/:id/actions/:name` | Runs an exporter's action (`VisionCore.Exporters.action/4`) with the document's `attributes` as its parameters, 60 s at most: 200 with the file as a download (`content-disposition: attachment`) for a file result, or with an `exporter-actions` resource whose attributes are the result for a JSON one; 404 for an unknown exporter or action, 409 when the exporter is busy or for another `data.type`, 503 when it does not run, 504 when it does not answer in time, 500 when the action fails (the error's `detail` says why), 400 without a document or for `attributes` that are no object. |
| `GET /api/ros2-node` | The ROS 2 node, `ros2-nodes` identified by its node name: `name`, `zenohEndpoint`, `connected`, related `topics` (`ros2-topics`: `name`, `messageType`, `rateHz`) and `services` (`ros2-services`: `name`, `serviceType`), in `included` with `include=topics,services` or either alone; 400 for any other include, 404 on a unit without the ROS 2 link (no `ros2:` section). |
| `GET /api/depth-preview` | The depth video (`VisionCore.Preview`): `depth-previews` `current`, with `colourRangeM`, the distance coloured blue, in metres, `0` for infinitely far; 503 while the previews do not run. |
| `PATCH /api/depth-preview` | Sets `colourRangeM`, a view setting of the unit that is not saved: 200 with the resource, 422 for a range outside 0 to 50, 409 on a `type` or `id` mismatch, 400 without `data.type`, `data.id` or `data.attributes.colourRangeM`, 503 while the previews do not run. |
| `GET /api/calibrations` | The calibrations in use (`VisionCore.Calibration.in_use/2`), one per target the unit can calibrate: `calibrations` identified by the stereo unit's prefix for its stereo pair, and by its name for each camera of its own. Each has `kind` (`stereo` or `camera`), `source` (`builtIn`, `stored` or `none`), `storedAt`, `canReset`, `cameras` (each one's `name`, `file`, `imageWidth`, `imageHeight`, `fx`, `fy`, `cx`, `cy`, `distortion` and `yaml`, `null` without a file) and, for a stereo pair, `baselineM` and `rectifiedFx`. Empty on a unit with nothing to calibrate. |
| `GET /api/calibrations/:id` | One of them, with its `error` when a file gives no calibration: 404 for an id that is none of the unit's targets, 503 when the stereo unit's calibration paths cannot be worked out. |
| `POST /api/calibration-sessions` | Starts a calibration session on the calibration its `calibration` relationship names, for `data.attributes.board`, `{columns, rows, squareMm}` in inner corners: 201 with the session; 400 without a `calibration`, 404 for one the unit has not, 422 for an invalid board or while the cameras do not run, 409 while a session runs. |
| `POST /api/calibration-solves` | Solves from the samples: 202 with the session `solving`, the outcome on the `calibration` channel; 422 before `goodEnough`. |
| `POST /api/calibration-applies` | Applies the solved calibration: 202 with the session `applying`, the outcome on the `calibration` channel; 422 before a solve. |
| `POST /api/calibration-cancels` | Ends the session: 201 with the session `idle`; 409 while applying. |
| `POST /api/calibration-resets` | Deletes the stored calibration of the `calibration` it names and returns to the built-in one, answering once the unit has taken it: 201 with the session; 400 without a `calibration`, 404 for one the unit has not, 422 without a store, with nothing stored or without a built-in calibration, 409 while a calibration session runs, 500 when the reset fails. The calibration actions also answer 404 on a unit with nothing to calibrate, 503 while the calibration session does not run, 403 for a document carrying an `id`, 409 for another `data.type` and 400 without one. |
| `GET /api/saved-calibrations` | The calibrations the unit keeps (`VisionCore.Calibration.saved/2`), as `saved-calibrations`, the newest first within each calibration, or one calibration's with `filter[calibration]`, none for an id that is no calibration's: 400 for any other `filter`, naming it in `source.parameter`. |
| `GET /api/saved-calibrations/:id` | One of them: 404 for one the unit does not keep, and for an id written another way than the unit writes it (`007`, `+7`), 503 while the unit's database cannot be reached. |
| `PATCH /api/saved-calibrations/:id` | Names it, from `data.attributes.name`: 200 with the resource; 400 without a name, 409 for another type or id, 422 for a name that is not 1 to 80 characters, 404, 503 while the database cannot be reached. |
| `DELETE /api/saved-calibrations/:id` | Removes it: 204; 409 for the calibration in force, 404, 503 while the database cannot be reached. |
| `POST /api/calibration-selections` | Puts the one its `savedCalibration` relationship names back in force, answering once the unit has taken it: 201; 400 without the relationship or without `data.type`, 403 for a document carrying an `id`, 404 for one the unit does not keep, 409 for another `data.type` or while a calibration session runs, 422 when the unit refuses its files, 500 when the selection fails, 503 while the database cannot be reached. |
| `GET /api/configuration` | The active vision configuration: `configurations` `current`, attribute `composer` holding `VisionCore.settings/0`, keyed by composer option names. |
| `GET /api/board` | The board the unit runs on (`OvcsVehicle.BoardStatus`): `boards` `current`, with `interfaces`, each running interface with a device and its `addresses`, `cpuPercent`, the CPU's busy share over half a second, `loadAverage`, the 1, 5 and 15 minute load averages, `memoryPercent`, the share of the memory in use, `time`, the clock's UTC time, and `clockSynchronized`, whether NTP synchronized it, `null` on a host. |
| `GET /api/firmware` | The firmware the unit runs (`OvcsVehicle.FirmwareInfo`): `firmwares` `current`, with `revision`, the commit it is built from, after the latest `v` version tag once there is one and `-dirty` when built with uncommitted changes, `target`, its Nerves target (`host` on a host), and `nervesSystem` and `nervesSystemVersion`, the Nerves system its `/usr/lib/os-release` names, `null` on a host, and `vehicle`, the vehicle's name, `null` without `VEHICLE`. |

Channels:

- `status`: a `VisionCore.Status` snapshot on join, then one a second, with each exporter's status (`level`: `ok`, `warning` or `off`, and `detail`, which for one that does not run says why), the API's own last, and each pipeline's times in `pipelines`: its `totalMs`, its `stages`' mean times and the `segments` computed as one. It carries no CPU load: that is the board's, in `GET /api/board`.
- `preview:left`, `preview:right`, `preview:depth` and `preview:<name>` for each camera of its own: JPEG frames as binary WebSocket messages, one at a time, sent when the client acknowledges the previous one with `ack`. Refused with `unknown stream` for a name that is none of the unit's cameras. The depth video's colour range is the unit's: `preview:depth` pushes it as a `depth_range` event, `{"metres": …}`, after every join and on every change, whichever client makes it with `PATCH /api/depth-preview`.
- `video:<name>`: the H.264 video of the camera `<name>` the unit relays, as binary `frame` events: a byte of flags, the capture time, the frame's size, then its NAL units. The client acknowledges each frame with `ack`; at most ten are unacknowledged. Refused with `unknown video` for a camera whose video is not relayed.
- `detections:<name>`: the detection pipeline `<name>`'s results, `detections:detection` for a detector without a name, at most its `maxHz` a second, as `detections` events. Each carries `captureUs`, the capture time of its frame, and every object's label, score, distance in metres and outline, as fractions of the width and height of the left camera's image. The API exporter's outputs list each one. A pipeline on a camera of its own outlines its objects on that camera's image, and an object it cannot place has a `null` distance. Refused when no pipeline of that name runs.
- `segmentation:<name>`: the segmentation pipeline `<name>`'s results, as binary `segmentation` events, at most its `maxHz` a second. Refused when no segmentation pipeline of that name runs.
  - Each event starts with eight little-endian 16-bit integers: the camera frame's size, the band of it the label grid covers and the grid's size. Then come the frame's capture time, in microseconds, as a little-endian signed 64-bit integer, and one class id byte a cell, row by row.
  - The channel sends each once the client acknowledges the previous one with `ack`, a newer result replacing the one waiting.
  - On every join, before any grid, a `classes` event names the classes, `labels` by class id, and `roadClasses`.
- `calibration`: each calibration in use as `calibration` events, with its `id`, on join and each time the unit takes another one, and the calibration session as `session` events, with the id of the `calibration` it works on, on join and on each change. A `saved` event carries the id of a `calibration` whose kept calibrations changed. Joining turns the unit's board detection on until the last client leaves. The channel takes no push. Refused with `nothing to calibrate` on a unit with no stereo pair nor camera, and with `unavailable` while the session does not run.

A channel answers an event it does not take with an error reply, `{"reason": "unknown event"}`, and stays joined. The socket takes connections from the pages the endpoint served itself: an `Origin` of another host, scheme or port is refused with a 403 (`check_origin: :conn`), except in development.

Any other path serves the dashboard.

On the vehicle, the endpoint serves HTTPS on port 443 with a self-signed certificate it generates at its first start (`VisionApi.SelfSignedCertificate`). It generates another when the stored pair cannot be read, does not match or names another host, and serves one held in memory when the files cannot be written. It redirects plain HTTP on ports 80 and 4100 to it (`VisionApiWeb.HttpsRedirect`); the vision firmware sets both in `config/target.exs`. In development it serves plain HTTP on 4101 on `localhost`, where a bridge's bus gateway takes 4100. In development it also answers cross-origin requests, for the dashboard's Vite dev server (`:allow_cross_origin` in `config/dev.exs`). `vision_api` holds no vehicle knowledge; [`../firmware`](../firmware) boots it with the vehicle's composer. See [Vision unit](../../docs/vision/README.md).
